One discount, two places

Applications say what was meant. Allocations say what happened. And two ways the totals will lie to you.

Lesson 01 ended with SAVE10 taking 12.00 off a hoodie. In GraphQL that one discount is written twice: once as a DiscountApplication on the order, the rule and its intent, and once as a DiscountAllocation on the line, the amount that landed. Merchants then stack a free shipping code and an automatic promotion on top, and the header numbers stop agreeing with each other. They are not wrong. Each field is answering a different question. This lesson teaches you which question each one answers, using the order from Lesson 01 with a cap added.

Recall from Lesson 01: subtotalPriceSet is the sum of line values, and a line value is originalTotalSet minus the sum of its discountAllocations. Only discounts move the subtotal. Hold that while the discount fields multiply.

The two places

fieldanswerslives on
discountApplicationswhat rules were applied, in what order, targeting whatthe order
discountAllocationshow much of each rule landed on this lineeach line item and shipping line
discountCodeswhich code strings the customer typed, nothing elsethe order

Shopify puts it plainly: "While DiscountApplication captures the discount's intentions and rules, the DiscountAllocation object shows the final calculated discount amount applied to each line."1 Each allocation points back to its application, whose index "indicate[s] the precedence of the discount application for calculations".2 Precedence matters in step 8.

Add these to the Lesson 01 query:

discountCodes
discountApplications(first: 10) {
  nodes {
    __typename index allocationMethod targetSelection targetType
    value { ... on MoneyV2 { amount } ... on PricingPercentageValue { percentage } }
    ... on DiscountCodeApplication  { code }
    ... on AutomaticDiscountApplication { title }
  }
}
shippingLines(first: 5) { nodes {
  discountedPriceSet { shopMoney { amount } }
  discountAllocations { allocatedAmountSet { shopMoney { amount } } discountApplication { index } }
} }

Step 6. A second line. The discount splits

Add a Cap at 25.00. SAVE10 has allocationMethod: ACROSS, "the value is spread across all entitled lines",3 so 10% of 145.00 = 14.50 spreads in proportion to line value.

Two things agree here and you should check them every time: the sum of allocations pointing at index 0 is what SAVE10 gave away; the sum of all allocations equals totalDiscountsSet; the sum of line values equals subtotalPriceSet. Notice targetSelection: ALL, "the discount is allocated onto all the lines".3 An order-wide code is still allocated line by line. That is why the per-line formula works.

Step 7. Free shipping. The first lie

Add FREESHIP. It targets the shipping line, not the products.

"discountApplications": { "nodes": [
  { "__typename": "DiscountCodeApplication", "index": 0, "code": "SAVE10", "targetType": "LINE_ITEM", "...": "" },
  { "__typename": "DiscountCodeApplication", "index": 1, "code": "FREESHIP",
    "value": { "percentage": 100.0 }, "allocationMethod": "EACH",
    "targetSelection": "ALL", "targetType": "SHIPPING_LINE" } ] },
"discountCodes": [ "SAVE10", "FREESHIP" ],
"shippingLines": { "nodes": [
  { "originalPriceSet":   { "shopMoney": { "amount": "12.0" } },
    "discountedPriceSet": { "shopMoney": { "amount": "0.0" } },
    "discountAllocations": [ { "allocatedAmountSet": { "shopMoney": { "amount": "12.0" } },
                               "discountApplication": { "index": 1 } } ],
    "taxLines": [] } ] },
"totalDiscountsSet":     { "shopMoney": { "amount": "26.5" } },
"totalShippingPriceSet": { "shopMoney": { "amount": "0.0" } },
"subtotalPriceSet":      { "shopMoney": { "amount": "130.5" } },
"totalTaxSet":           { "shopMoney": { "amount": "15.66" } },
"totalPriceSet":         { "shopMoney": { "amount": "146.16" } }

Watch what moved and what did not:

  1. subtotalPriceSet stayed at 130.50. Shipping discounts live on the total side of the chain.
  2. totalDiscountsSet jumped to 26.50. It mixes product and shipping discounts into one number.
  3. Shipping tax vanished. Tax is charged on discountedPriceSet, now 0.00. Total: 130.50 + 0.00 + 15.66 = 146.16.

This is the first lie: if you subtract totalDiscountsSet from anything that already contains shipping, you remove the 12.00 twice. The clean way to tell the two kinds apart is targetType: LINE_ITEM or SHIPPING_LINE.2 discountCodes cannot help; it is a list of strings.4

Step 8. An automatic discount. The second lie

The merchant runs an automatic discount: 5.00 off each hoodie. Shopify applies product discounts first and order discounts "to the revised subtotal after product discounts".5 So the automatic one takes index 0, and SAVE10 works on the reduced prices.

"discountApplications": { "nodes": [
  { "__typename": "AutomaticDiscountApplication", "index": 0, "title": "Hoodie Season",
    "value": { "amount": "5.0" }, "allocationMethod": "EACH",
    "targetSelection": "ENTITLED", "targetType": "LINE_ITEM" },
  { "__typename": "DiscountCodeApplication", "index": 1, "code": "SAVE10",
    "value": { "percentage": 10.0 }, "allocationMethod": "ACROSS",
    "targetSelection": "ALL", "targetType": "LINE_ITEM" },
  { "__typename": "DiscountCodeApplication", "index": 2, "code": "FREESHIP",
    "value": { "percentage": 100.0 }, "targetType": "SHIPPING_LINE" } ] },
"discountCodes": [ "SAVE10", "FREESHIP" ],
"lineItems": { "nodes": [
  { "title": "Hoodie", "originalTotalSet": { "shopMoney": { "amount": "120.0" } },
    "discountAllocations": [
      { "allocatedAmountSet": { "shopMoney": { "amount": "10.0" } }, "discountApplication": { "index": 0 } },
      { "allocatedAmountSet": { "shopMoney": { "amount": "11.0" } }, "discountApplication": { "index": 1 } } ] },

"totalDiscountsSet": { "shopMoney": { "amount": "35.5" } },

discountApplications.nodes lineItems[Hoodie].discountAllocations [0] Automatic 5.00 EACH ENTITLED ◀──── { 10.00, discountApplication.index 0 } [1] SAVE10 10% ACROSS ALL ◀──── { 11.00, discountApplication.index 1 } line value 99.00 [2] FREESHIP 100% SHIPPING_LINE ◀──── shippingLines[0].discountAllocations { 12.00, index 2 }

The shape changed, not just the numbers:

  1. The automatic discount took index 0. Every other index shifted by one. Match allocations to applications by the discountApplication.index in the same response; never store indexes.
  2. discountCodes does not mention it. It reads ["SAVE10", "FREESHIP"] before and after. Only discountApplications knows about "Hoodie Season", and only through __typename and title. This is the second lie: codes are what the customer typed, not what was discounted.
  3. SAVE10 shrank from 14.50 to 13.50. It applied to 110.00 + 25.00, not 145.00. Whether two discounts stack at all depends on the merchant's combination settings; a customer can enter up to 5 product or order codes and 1 shipping code.5

Hoodie line value: 120.00 − 21.00 = 99.00. Cap: 22.50. Subtotal 121.50. Tax 11.88 + 2.70 = 14.58. Total 121.50 + 0.00 + 14.58 = 136.08.

⚠ What this means for cashback
A per-line base reads originalTotalSet minus the line's allocations and never touches totalDiscountsSet, so both lies are avoided for free. If a Smile reward code should be excluded from the base or counted separately, match its allocations by index; the allocation carries the amount, the application carries the code.
