Linguagem Ubíqua

Faça o código falar as palavras do negócio — a ideia que destrava o DDD.

DDD costuma ser confundido com "entidades + repositórios". Mas Eric Evans, revisitando o próprio livro, coloca o design estratégico — Linguagem Ubíqua, Bounded Context, Core Domain — no centro, com os building blocks apenas "em órbita".3 A Linguagem Ubíqua é a porta de entrada: não exige framework nenhum, é usável na próxima daily, e sem ela você nem consegue traçar um contexto ou nomear um aggregate.

O que é

Uma linguagem comum e rigorosa, construída entre desenvolvedores e usuários, baseada no domain model usado no software — rigorosa porque "software não lida bem com ambiguidade".1

É uma língua só, falada por especialistas de negócio e devs, presente na conversa e escrita no código, nos testes e nos diagramas. Modelo e linguagem são o mesmo artefato: testar a linguagem conversando com o especialista é testar o modelo.1

Por que importa

Quando o código diz status = 2 mas o negócio diz "a recompensa foi resgatada", alguém paga o custo da tradução em toda leitura, todo bug, todo onboarding. Esse buraco entre a fala e o código é onde os defeitos se criam.

Um PointsTransaction que mistura "cliente ganhou pontos", "resgatou recompensa" e "pontos expiraram" é um saco ambíguo. Deixe os verbos do especialista guiarem o código — os nomes das classes viram as mesmas palavras ditas na daily.

Como conecta com Bounded Context

Uma Linguagem Ubíqua só é unívoca dentro de uma fronteira.2 No smile-core, pegue a palavra "Points": no contexto de Earning, é o que o cliente acumula; no de Billing, pode ser uma métrica de uso que define o quanto o lojista paga. Mesma palavra, dois modelos. O momento em que a mesma palavra significa coisas diferentes é onde nasce uma fronteira de contexto.2

⚠ A armadilha em Rails: Anemic Domain Model
Um objeto Reward só com getters/setters, e toda a lógica num service object, é um Anemic Domain Model:4 parece falar a linguagem, mas não carrega comportamento. Fowler chama de design procedural fantasiado de OO — derrota o propósito do modelo. É o estilo padrão de "fat service objects sobre ActiveRecord passivo". Cuidado.
