Design-level Event Storming

Da faixa "Store Credit" pros aggregates, comandos e policies — e daí pro primeiro esqueleto de app/components/.

O Big Picture da Lição 03 te deixou com faixas e hotspots. Agora você escolhe uma faixa e dá zoom: o Software Design Event Storming pergunta, pra cada evento laranja, o que causou isso (um comando) e quem decidiu executar (um aggregate). O resultado não é um diagrama pra guardar — é literalmente a lista de arquivos do primeiro componente. E a regra que decide o tamanho de cada aggregate vem de uma frase de Vernon que você vai carregar pro resto da carreira: uma instância de aggregate por transação.

Recuperando a Lição 03: laranja é evento (passado), azul é comando, lilás é policy ("sempre que X, então Y"), rosa-largo é sistema externo, rosa-neon é hotspot. Amarelo-pálido grande — o aggregate — ficou reservado pra esta lição. Brandolini o define como "a porção do sistema que recebe comandos e decide se os executa".3

A sequência: do evento pro aggregate

Khononov organiza o zoom em passos, e a ordem importa porque cada cor puxa a próxima:1

  1. Comandos. Pra cada evento, o que o causou? Cole o azul antes do laranja: "Emitir crédito" → "Crédito emitido". Anote quem dá o comando (ator amarelo) ou se é o sistema.
  2. Policies. Onde um evento causa um comando sem humano no meio, cole o lilás entre os dois: "Sempre que promoção aplicada ao pedido, então emitir crédito". Isso é o que vai ligar dois aggregates diferentes.
  3. Read models. O que o ator precisa ver pra decidir dar o comando? "Saldo disponível" antes de "Resgatar crédito". Verde.
  4. Sistemas externos. Quem de fora recebe ou origina eventos, e o que ele garante ou não garante.
  5. Aggregates. Agrupe cada comando com os eventos que ele produz e dê um nome do glossário. "Comece a adicionar aggregates como donos do comportamento de negócio."2

A regra que decide o tamanho

"Um bounded context bem projetado modifica só uma instância de aggregate por transação, em todos os casos. […] Aggregate é sinônimo de fronteira de consistência transacional."4

Vernon conta o caso de um Product que segurava backlog items, releases e sprints porque "produtos têm essas coisas" — e falhava em produção toda vez que dois usuários mexiam em partes diferentes ao mesmo tempo. O erro: invariantes falsos, nascidos de conveniência de composição, não de regra de negócio.4 A pergunta certa pra cada fronteira é: o que precisa ser verdade no fim desta transação?

E quando não estiver claro, o desempate que Evans deu a Vernon: "pergunte se é trabalho do usuário que está executando o caso de uso deixar os dados consistentes. Se for, transacional. Se for trabalho de outro usuário, ou do sistema, eventual."5 Aplique na sua faixa:

Regra do muralDe quem é o trabalho?Veredito
"Resgate não pode exceder o saldo"Do shopper que está resgatando — ele precisa ver o resultado agoraTransacional. Saldo e resgate no mesmo aggregate: Conta de crédito.
"Promoção aplicada ao pedido gera crédito"Do sistema — o shopper só fez um pedidoEventual. Dois aggregates (Promoção, Conta de crédito) ligados por uma policy.

Exemplo: a faixa Store Credit com zoom

Command Aggregate Event Policy Read model External
Fluxo 1 — emissão (disparado por outro contexto) Promoção aplicada ao pedido → Sempre que promoção aplicada, então emitir crédito → Emitir crédito → Conta de crédito → Crédito emitido → Sempre que crédito emitido, então espelhar → Shopify StoreCreditAccount → Crédito espelhado
Fluxo 2 — resgate (disparado pelo shopper) Shopper Saldo disponível → Resgatar crédito → Conta de crédito → Crédito resgatado Resgate acontece na Smile ou só na Shopify?
Fluxo 3 — expiração (disparado pelo tempo) Sempre que passa a data, então expirar → Expirar crédito → Conta de crédito → Crédito expirado Reembolso do pedido estorna? Quem manda?

Três comandos, um aggregate: Conta de crédito recebe "emitir", "resgatar" e "expirar", e é a única coisa que sabe o saldo. A Promoção é outro aggregate, em outra faixa, e nunca aparece dentro deste — só o promotion_id viaja no evento. Repare no hotspot do Fluxo 2: ele é o mesmo "vive na Shopify ou na Smile?" da Lição 03, agora com uma pergunta precisa. Enquanto estiver aberto, "Resgatar crédito" pode nem ser um comando seu — pode ser um evento que chega da Shopify.

A ponte pro código: o esqueleto do componente

Cada post-it do mural tem um lugar na convenção de pastas do smile-core. A pasta do componente é o namespace; as pastas de camada (models/, controllers/) "são só organização e não adicionam segmento à constante".7

app/components/store_credit/
  CONTEXT.md                          ← glossário (### Language) + invariantes (### Current design)
  models/
    account.rb                        → StoreCredit::Account          (aggregate root)
    account/entry.rb                  → StoreCredit::Account::Entry   (filha: crédito, resgate, expiração)
  promotion_applied/
    issue_credit_consumer.rb          → StoreCredit::PromotionApplied::IssueCreditConsumer  (a policy)
  jobs/
    account/issue_credit_job.rb       → StoreCredit::Account::IssueCreditJob
    account/expire_job.rb             → StoreCredit::Account::ExpireJob
  shopify/
    mirror.rb                         → StoreCredit::Shopify::Mirror   (adapter pro sistema externo)

O aggregate root recebe os comandos como métodos públicos com verbo de domínio — a regra P1/P2 dos fizzy-patterns: nada de StoreCreditService.process.7 O invariante transacional mora dentro do verbo. O evento é publicado depois do commit, no tópico com nome no passado, do jeito que o smile-core já faz (smile_platform.customer_signed_up, smile_platform.points_transaction_created):

module StoreCredit
  class Account < ApplicationRecord
    has_many :entries, dependent: :destroy   # mesma fronteira → OK

    class InsufficientBalance < StandardError; end

    def issue!(amount, promotion_id:, expires_at:)
      transaction do                          # UMA instância de aggregate por transação
        entries.create!(kind: :credit, amount:, promotion_id:, expires_at:)
        update!(balance: balance + amount)
      end
      DomainEventPublisher.publish(CreditIssued.new(self, amount:, promotion_id:))
    end

    def redeem!(amount)
      raise InsufficientBalance if amount > balance   # o invariante verdadeiro
      transaction do
        entries.create!(kind: :redemption, amount: -amount)
        update!(balance: balance - amount)
      end
      DomainEventPublisher.publish(CreditRedeemed.new(self, amount:))
    end
  end
end

A policy "sempre que promoção aplicada, então emitir crédito" vira um consumer fino: lê o evento de outro contexto e enfileira um job que chama o verbo — exatamente a forma que o smile-core usa em MerchantNotifications::DeadOfflineTokenEmail::Consumer.7 Nome: <EventoNoPassado>::<Verbo>Consumer.

module StoreCredit
  module PromotionApplied
    class IssueCreditConsumer < SingleMessageConsumer   # tópico: smile_platform.promotion_applied
      def consume_message(message)
        event = message.payload.fetch(:event)
        Account::IssueCreditJob.perform_later(
          event.fetch(:customer_id), event.fetch(:promotion_id), event.fetch(:amount)
        )
      end
    end
  end
end
⚠ A armadilha: o aggregate gigante, versão Rails
A tentação vai ser Promotion has_many :credits, dependent: :destroy. Isso é o Product de Vernon: "promoções têm créditos" virando fronteira de transação — e agora apagar uma promoção apaga saldo de shopper. A regra 3 de Vernon é referenciar outro aggregate por identidade:5 a Conta guarda promotion_id numa coluna, sem foreign key no banco e sem has_one cruzando componentes — a direção que o smile-core já adotou pra módulos.7 Se você precisou de um transaction do envolvendo models de dois componentes, a fronteira está errada.

Isso não é Event Sourcing: o estado vive na coluna balance e nas entries (um livro-caixa comum); os eventos publicados são comunicação entre contextos, não a fonte da verdade. A missão deixou Event Sourcing de fora de propósito.
